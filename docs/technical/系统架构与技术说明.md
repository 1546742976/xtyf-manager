# 系统架构与技术说明

**基准**：2026-10-13，仓库 `main` 已实现逻辑。以下架构描述源代码，不保证生产实例已升级。

## 1. 整体形态

    浏览器（Jinja 模板 + 原生 JS/CSS）
         |
         v
    Flask app.py（登录 / 页面 / 基础接口）
         +-- common.py：会话、RBAC、SQLite 请求连接
         +-- modules/task_*.py：任务、依赖、修订、迁移、截图
         +-- modules/task_catalogs.py：专业组、造车组别与成员关联
         +-- modules/member_profiles.py：资料编辑、成员软删除/恢复
         +-- modules/discussions.py：本地话题、消息、附件与未读
         +-- modules/funds.py：独立资金 SQLite
         +-- modules/invoices.py：PDF + JSON 元数据 + SSE 后台任务
         |
         +-- data.db
         +-- data/funds/funds.db、资金管理记录.txt
         +-- data/invoices/（PDF + JSON + 临时上传）
         +-- data/task_attachments/（受控截图）

生产部署模板为 **Gunicorn 1 worker / 8 threads / HTTP**（`deploy/rm-progress.service`）；发票任务状态保存在主库 `invoice_jobs`，`modules/invoice_storage.py` 使用同机跨进程文件锁，`deploy/gunicorn.conf.py` 启动队列消费线程。默认 worker 数量保持不变，多进程运行待验收。Flask 本地开发端口默认 8520。

## 2. 两类组别及成员身份

- `members.id` 是稳定自增主键；`username` 是唯一且可修改的登录名；真实姓名由管理员统一维护。
- `groups` + `member_groups`：**专业组**，描述技能方向；成员可多选。
- `projects` + `member_projects`：**造车组别**，描述机器人归属；成员可多选。
- `tasks.project_id`：**每个任务最多一个造车组别**；它不自动跟随负责人的专业组，也不再通过 `task_groups` 创建任务专业组标签。
- 目录名称可增改，关联通过 ID 保持稳定。成员、专业组和造车组别使用 `deleted_at` 软删除；恢复不重建 ID。
- `owner_id` 表示一个总负责人，`task_participants` 可包含多个成员；成员的专业组和车组关联不是权限角色，权限仍由 `role` 决定。

## 3. 任务协作

    tasks --parent_id--> tasks       主前置依赖（保留历史字段名）
          --dependencies--> tasks    其他前置依赖（联合检查无环）
          --owner_id--> members      总负责人
          --participants--> members  参与者
          --revisions--> changes     字段级历史与管理员安全撤销
          --attachments--> files     受控私有截图

- 管理员/项管可以创建或管理任务；负责人和参与者可以更新其参与任务的一般设置及前置依赖，但不能修改负责人、参与者和造车组别等归属字段。
- 更新包含 `version`，陈旧写入返回冲突；管理员撤销也要求无后续字段修改冲突。
- 任务删除只设置 `deleted_at`，保留日志、修订和截图元数据；删除前校验后续任务的主前置与其他前置引用。**尚无用户级任务恢复接口**。
- 截图单次最多 5 张，每张最多 10 MiB，支持经内容校验的 PNG/JPEG/WebP，文件不置于公开静态目录。

## 4. 数据存储与迁移

| 数据 | 保存位置 | 重要约束 |
| --- | --- | --- |
| 成员、角色、任务、修订、组别、登录失败记录 | `data.db` | SQLite、`session_version` 撤销其他会话 |
| 资金流水、审核结果 | `data/funds/funds.db` | `amount_cents` 整数分；`version` 审核快照校验；`member_permissions` 的 `funds.review` + 后端角色校验 |
| 发票后台任务及进度 | `data.db` 的 `invoice_jobs` | 与后台任务审计同事务保存；排队任务自动接续 |
| 发票与元数据 | `data/invoices/` | PDF 文件、`.invoice_meta.json`、`.invoice_cache.json` |
| 工作截图 | `data/task_attachments/` | 必须随主库组成一致性恢复点 |
| Flask 会话签名密钥 | `secret.key` | 不入库也不能提交 Git |

`modules/task_migrations.py` 使用 `schema_migrations` 维护 v1～v8 数据升级：v1 补任务层级、版本及关系；v2 拆分旧“视觉;电控”组合名并一次性预置默认专业组；v3 增加成员与造车组别的多对多关系，并从历史任务的负责人与参与者关联中**一次性**推断车组；v4 新增可空的 `schedule_stage`，仅在手动应用排期时保存多专业组任务的阶段选择，不自动改动旧日期；v5 增加默认银白的账户主题 `ui_theme`；v6 增加 `start_date_origin`，旧任务以 frozen 初始化且日期不重算；v7 增加 `completed_at`，只记录真实完成时间，不用最后修改时间推断历史完成日期。v8 增加默认关闭的 `schedule_locked`，不将历史日期来源解释成固定标记，不改既有日期。多次运行不应反复覆盖后续人工修改。历史 `task_groups` 仅用于兼容，不再是任务车组字段。

## 5. 入口与 API

账户主题保留 v5 的 `ui_theme` 作为亮暗兼容字段，由 `modules/workspace_settings.py` 的幂等迁移新增 `theme_mode/light_theme/dark_theme` 和单例目标表。`GET/POST /api/account/preferences` 仅读写本人，支持八套配色和系统模式；同步 head 脚本根据 OS 在首次绘制前选择具体配色。倒计时 `GET/PUT /api/workspace/countdown` 使用北京时间，管理员写入需版本、登录和 CSRF。日常项目入口合并到 `/tasks?type=daily`，独立数据模型不变。

| 范围 | 路径 | 内容 |
| --- | --- | --- |
| 页面 | `/`、`/tasks`、`/manage`、`/members`、`/account` | 工作台、任务、成员与账户 |
| 协作 | `/api/data`、`/api/task`、`/api/task/<id>`、`/api/task/<id>/delete` | 任务读取、创建、编辑、逻辑删除 |
| 历史 | `/api/task/<id>/logs`、`/api/task/<id>/revisions`、`.../revert` | 日志、修订和管理员撤销 |
| 任务文件 | `/api/task/<id>/attachments` | 上传、读取、删除均带权限检查 |
| 目录 | `/api/groups`、`/api/projects` | 两套字典及软删除/恢复 |
| 成员 | `/api/members`、`/api/member`、`/api/members/import` | 列表、新建、导入 |
| 档案 | `/api/account/profile`、`/api/member/<id>/profile` | 本人/管理员资料编辑 |
| 成员归档 | `/api/member/<id>/delete`、`/api/member/<id>/restore` | 管理员软删除/恢复 |
| 资金 | `/funds/api/records`、`/funds/api/stats`、`/funds/api/export` | 台账、审核、统计 |
| 发票 | `/invoices/api/...`、`/invoices/file/<path>` | 上传、确认、归档、统计、导出 |
| 协作 | `/discussions` | 全员本地话题、任意格式附件、撤回和未读，不连接 GitHub |

接口的 HTTP 方法、请求数据和边界校验以对应 `modules/*.py` 和 `tests/` 为准；更详细的账户 API 参阅[成员资料与账号编辑](成员资料及账号修改.md)。

## 6. 安全与限制

依赖排期使用 `/api/projects/<id>/schedule/preview` 和 `/schedule/apply` 两个 POST 接口，规则版本为 2。预览在读事务中加载本车组任务、两类前置与引用的外部任务，并读取本组有效任务负责人在其他车组及未归属车组的有效任务；按依赖顺序计算提前最多两天的衔接，默认只顺延。签名快照绑定这些数据和本次基准日、选择及工期。应用在 `BEGIN IMMEDIATE` 中重新校验、计算并一次性保存日期、修订和日志，变化返回 409。固定与进行中任务默认保护；同一负责人日期重叠仅提示，外部任务只读参考。权限和 CSRF 保留。接口字段和规则见 [任务排期](../usage/任务排期.md)。

- 后端强制校验身份、角色和业务资源权限；前端隐藏按钮不构成授权。
- 登录按 IP+用户名组合限流；资料中的用户名、角色、密码及账户状态修改可使其他会话失效。
- 发票归属仅以 `submitter_id` 授权；历史唯一姓名一次性迁移，同名或无法匹配的记录须由财务选择成员 ID 确认。
- `modules/security.py` 统一处理会话 CSRF、首次改密限制、成员 ID 财务权限与请求/后台任务审计；`/admin/security` 提供管理入口。资金金额与发票金额已统一为十进制逐笔舍入、整数分计算及两位文本输出；金额迁移/一致性测试尚待验收。发票 JSON 的读改写由同机文件锁串行保护，后台任务与审计同库持久化；PDF 与 JSON 之间仍不是跨文件事务，整理/删除中断需人工核对。
- 当前 HTTP 不对传输提供机密性保护，必须由部署方限制访问范围。

## 推进规则与增量数据（2026-10-18）

任务状态、进度和完成时间在同一事务维护，并作为一组修订字段参与撤销与冲突检查。日常项目普通更新只递增本组版本，状态转移才同时递增项目版本；手动完成、重新打开与启停组校验完整组版本快照。

日常项目保留 `(project_id, stage)` 身份，增补专业组目录 ID 和名称快照。新完整组请求使用 `groups_mode=replace`；旧请求保留动态组。历史三组由管理者通过 `group_links` 明确关联，启动迁移不猜测目录映射、不修正历史状态。

新增 `/api/task-alerts` 管理聚合接口，任务及日常项目的 `/topics` 关联接口和 `/blocker` 阻塞接口。话题正文始终引用原消息，撤回后遮蔽；关联操作只更新事项版本和独立操作记录，不伪造进度。现有进度 URL、附件与历史记录保留。

升级迁移仅增加字段和表；回滚代码不会撤销业务数据。使用动态组之后回退到旧代码前，需要核对旧版本兼容性及配套数据快照，不能自动丢弃新数据。
