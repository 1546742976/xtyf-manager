# 第三轮安全与可靠性修复（2026-10-12）

本轮以合并到 main 的上一轮全站 UI 重构为基线，不迁移已有发票或资金数据库。

## 已实施

- 发票临时上传按账号 ID 隔离到 .uploads/账号ID/，随机文件名前缀，文件入库和清理必须验证本人暂存目录；防止用已入库文件路径再次确认、跨账号访问暂存文件。
- 新发票元数据增加 submitter_id（唯一成员 ID）；本人列表、统计及预览严格比对 ID。管理员修改提交人时，只有姓名匹配唯一有效成员才写 ID，否则为 0，避免同名串权。
- 单张/批量上传检查 PDF 文件头，入库金额校验为有限非负值；单次批量确认最多 200 张。
- 查重路径需经过归属校验，成员仅得到重复类型、不返回别人文件路径；元数据单张和批量修改校验合法状态、字段白名单与目标文件是否存在。
- 状态切换后移除旧元数据路径键，写入新路径键，修复旧路径记录残留。
- 登录失败计数落在进度 SQLite 内，按 IP + 用户名组合计数：15 分钟内失败 6 次后锁定 15 分钟；不直接信任 X-Forwarded-For。
- 成员表新增 session_version，重置密码、停用、角色调整会让既有会话失效；自行改密保留当前会话但使其他设备退出。
- 为上述路径新增后端回归测试。

## 上线前事项

1. 备份 data.db、data/funds/funds.db、data/invoices/、secret.key。
2. 上线后用户此前登录的旧会话需要重新登录，这是 session_version 生效后的预期行为。
3. 旧版根目录 .uploads/ 中未确认的临时文件不再允许从浏览器确认入库；需要重新上传。已经入库的 PDF 保持原状。
4. 现有任务和资金 API 路径、Flask app:app 入口保持不变；发票元数据 JSON 无需批量迁移。
5. 运行 python -m unittest discover -s tests -v，以及 Python/JS 语法检查，然后人工验证上传、查重、预览、状态变更、成员密码重置。

## 尚未解决

- 本项目按现有 HTTP 部署，不将 HTTPS/TLS 支持列入后续开发范围。HTTP 不加密登录密码、会话 Cookie 和业务数据，不宜直接暴露在不可信公网；需要由部署方限制访问范围（如可信内网、VPN、服务端 IP 访问控制），且仍需完成 CSRF 防护。纯 HTTP 环境不能直接强制 Secure Cookie，否则可能影响登录。
- 历史发票仍没有 submitter_id 时继续按姓名兼容，存在重名/改名歧义；需人工核实归属后另行迁移，不在本轮猜测关联。
- 发票 .invoice_meta.json 并发写入可能丢数据，后台任务还在单进程内存，仍必须使用单 Gunicorn worker。
- 金额存储是 REAL 而非整数分，资金操作审计日志尚未建成。
- 需要浏览器 E2E 与部署备份恢复演练。
