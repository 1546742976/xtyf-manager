# 打包、手动上传与服务器更新

这套流程用于已经通过 `deploy/deploy.sh` 安装的默认 Linux/systemd 部署：服务名 `rm-progress`、运行目录 `/opt/rm-progress`、登录入口 `http://127.0.0.1/login`。默认部署可不传参数；定制监听地址应提供健康检查 URL。

本地仅需要 Python 3.11+ 和 Git；服务器需要 Python 3.11+、`python3-venv`、systemd、sudo，以及访问 Python 包源的网络。服务须正在运行且使用非 root 用户。首次安装仍使用 `deploy/deploy.sh`。

## 1. 本地打包当前 commit

先把要发布的修改提交到 Git，包括首次加入的这两个脚本。脚本固定打包 **HEAD**，不会把未提交的修改或未跟踪文件混入发布包；不要求 push，也不会自动 commit。

在仓库根目录执行：

```powershell
python deploy/package_release.py
```

Linux/macOS 可以使用 `python3 deploy/package_release.py`。输出位于仓库 `dist/`：

```text
dist/
  xtyf-manager-<12位commit>.tar.gz
  xtyf-manager-<12位commit>.tar.gz.sha256
```

压缩包内有同名顶层目录，包含当前 commit 的代码和 `release-manifest.json`（完整 commit、每个代码文件的 SHA-256）。`dist/` 已被 Git 忽略。打包时会拒绝 Git 中已跟踪的常见运行时数据路径、数据库、密钥和链接文件。

重复打包同一 commit 时，若输出文件已存在会停止，不覆盖旧包。可以直接复用原包，或先把原输出移走后重新运行。若提示 HEAD 缺少发布脚本，说明脚本尚未提交：提交后再运行即可。

## 2. 手动上传，然后在服务器解压

通过 MobaXterm 左侧 SFTP 文件面板，把 **tar.gz 和 sha256 两个文件**上传到应用用户的 `~/progress_releases/`。先在终端创建目录：

```bash
mkdir -p ~/progress_releases
cd ~/progress_releases
```

下面的 `<12位commit>` 替换为实际文件名里的短提交号：

```bash
sha256sum -c xtyf-manager-<12位commit>.tar.gz.sha256
tar -xzf xtyf-manager-<12位commit>.tar.gz
cd xtyf-manager-<12位commit>
```

必须先看到校验结果 `OK` 再解压。解压目标应是全新的独立目录；不要解压到 `/opt/rm-progress`，也不要用发布包覆盖旧源码目录。只有解压不会影响线上服务。

## 3. 在解压目录运行更新脚本

安排维护时间，暂停其他导入程序、开发服务、定时写入任务和人工数据库操作。脚本会停止 `rm-progress` 并检查以运行目录为工作目录的残留 Python/Gunicorn 进程，但不能自动识别所有其他写入者。

```bash
sudo python3 deploy/update_release.py
```

脚本从自身所在的解压目录读取清单和代码，自动识别现有服务用户及其 home，不需要指定版本、压缩包路径或账号。

需要安装依赖时，更新脚本默认使用清华 PyPI 镜像 `https://pypi.tuna.tsinghua.edu.cn/simple`，仅为本次 pip 安装指定源，不修改服务器全局 pip 配置。若传入非空环境变量 `PIP_INDEX_URL`，则优先使用该地址；不会自动轮换镜像。使用 sudo 时将变量显式传给更新进程，例如改用中科大源：

```bash
sudo env PIP_INDEX_URL=https://mirrors.ustc.edu.cn/pypi/simple python3 deploy/update_release.py
```

依赖未变化时仍复用现有虚拟环境，不访问包源。镜像地址可参阅[清华镜像使用帮助](https://mirrors.tuna.tsinghua.edu.cn/help/pypi/)和[中科大镜像使用帮助](https://mirrors.ustc.edu.cn/help/pypi.html)。

它会先暂停邮件 timer 并等待已有发送批次完成（以确保邮件数据库和附件快照一致），升级成功或回滚后恢复原先的 timer 运行状态；从不自行启用原本未启用的 timer。SMTP 配置固定在 `/etc/xtyf-manager/mail.env`，不随发布包覆盖。

它依次执行：

1. 校验发布文件、现有部署、默认数据路径和服务配置兼容性；编译新版 Python 文件。
2. 准备依赖：`requirements.txt` 未变化时直接复用现有虚拟环境，不执行 pip、不下载依赖；变化时在旧服务仍在线期间创建独立环境并安装新版依赖。输出实时显示并写入备份目录的 `dependencies.log`，每 15 秒显示进度提示，总超时为 15 分钟。失败或取消时旧服务不受影响，安装子进程会被终止。
3. 依赖准备完成后停止服务，创建时间戳备份，保存完整数据快照、旧代码、有效服务配置和运行环境。快照验证后恢复到隔离目录。旧虚拟环境不被修改。
4. 将快照数据放入新版暂存目录，以应用用户加载应用，执行内置迁移。检查两个数据库完整性、成员/任务/日志/资金记录 ID、PDF/任务附件和会话密钥；这些检查不替代业务验收。
5. 把整个旧运行目录保留为 `/opt/rm-progress.previous-<时间戳>`，把新版切换到 `/opt/rm-progress`。现有 systemd 配置保持不变。
6. 自动安装/更新邮件 systemd unit 与网站环境 drop-in；启动网站，等待登录入口返回 HTTP 200，输出 `DEPLOYMENT_OK`、版本及备份位置。

下载依赖在停服前进行，耗时取决于网络和依赖安装；无需重装的更新直接进入备份。停服后的阶段可以按一次 Ctrl+C 取消并恢复旧服务，恢复期间会暂时忽略后续 Ctrl+C/SIGTERM，直到恢复确认结束。若新旧 `rm-progress.service` 模板发生变化，升级器会先核对当前安装的 systemd 主服务文件是否与旧版模板生成结果一致：一致时自动升级主服务配置（例如 Gunicorn 的 `--timeout 120` → `240`），保留原文件备份并在回滚时恢复；若存在人工定制、符号链接或非标准安装位置，则在停服前拒绝覆盖，并要求人工审核。独立 drop-in 不受影响。运行数据通过环境变量指向默认目录之外时，仍需人工处理；环境变量路径必须使用绝对路径。

新版数据来自更新时的服务器快照。解压目录只作为发布源；旧的 `~/progress_system/` 不再自动同步，后续更新仍应解压到新目录运行脚本。

## 4. 备份和结果在哪里

```text
<应用用户home>/progress_backups/upgrade-<时间戳>/
  full-data.zip             主库、资金库/台账、发票/隐藏元数据/上传、任务附件和密钥
  restored/                 备份恢复副本
  old-code/                 升级前代码与其他配置文件
  service.txt               有效 systemd 配置
  rm-progress.service        旧版主服务文件（仅发生模板变更时）
  runtime-environment.json  运行环境，可能包含凭据，保持私有
  dependencies.log          新环境依赖安装日志
  recovery.json             旧运行目录位置及数据数量
  result.json               成功结果
```

实际运行目录内的 `DEPLOYED_COMMIT` 记录部署版本。依赖变化时，`/opt/rm-progress-venv-<时间戳>` 是独立依赖环境；依赖未变化时，新应用的 `venv` 链接到仍然保留的旧虚拟环境（可能位于某个 `rm-progress.previous-*` 目录内）。不要删除正在使用的环境或包含它的旧目录。旧运行目录及历史备份保留，不自动清理。旧 `backups/` 如存在，会通过链接继续保留，不能随意删除它所在的旧运行目录。

出现异常时，脚本会尝试停止新服务、恢复旧目录并重新启动旧服务。失败的新目录保留为 `/opt/rm-progress.failed-<时间戳>`，便于检查。若机器断电、脚本被强制杀死或回退本身失败，需要人工恢复；不能把自动回退视为断电恢复保证。

## 5. 人工恢复

先查看备份目录的 `recovery.json` 并核对实际路径。停止服务和所有其他写入者，将当前 `/opt/rm-progress` **改名保留**，再将对应的 `/opt/rm-progress.previous-<时间戳>` 改回 `/opt/rm-progress`，随后启动 `rm-progress`。不要只切换旧代码而继续使用已经迁移的新数据库。

旧目录是升级前的整套运行状态，恢复它会回到升级前的数据。新版启动后如果已经产生业务写入，先保留新目录和数据再决定如何合并，不能直接丢弃。若旧目录不可用，参照[发布检查与数据恢复](发布检查与数据恢复.md)从完整快照恢复。

上线完成后可由管理员检查实际业务页面。HTTP 200 只证明入口启动成功，不代表已验证所有业务功能。

## 2026-10-22 发布工具调整

`update_release.py --health-url http://127.0.0.1:8520/login` 可覆盖默认检查地址，升级与失败回滚都使用同一地址；仅允许 HTTP(S)，不能嵌入凭据。依赖来自固定版本 requirements.txt；Gunicorn 仅在非 Windows 安装，不再重复执行未固定版本安装。

Android JKS 和密码文件就是发布身份，必须离线备份。默认缺失任一个即停止；只有显式 `--init-signing-key` 且 `XTYF_CONFIRM_NEW_SIGNING_KEY=1` 才初始化新身份。`--test-signing` 使用临时身份，正式发布拒收。报告记录实际签名证书 SHA-256、验签和 zipalign 结果；证书改变默认阻断，没有历史指纹时标注“无可比较基线”，不表示发布身份已验证。详见客户端说明。

systemd 模板增加 NoNewPrivileges、ProtectSystem=strict、PrivateTmp，并保留应用根目录可写（SQLite WAL/SHM 与密钥原子替换需要父目录写权限），源码子目录只读。定制数据库、日志、附件等位于应用目录之外时，必须补充对应 ReadWritePaths；部署前在 staging 验证。邮件 timer 改为 60 秒。本轮仅语法与隔离检查，未启动生产 unit、未部署、未生成源码包或安装包。
