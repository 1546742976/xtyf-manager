# 发布检查与数据恢复

**重要**：以下为运维流程，不是自动执行脚本。仓库更新/PR 合并与实际生产发布是两回事。先确认实际部署的提交、数据路径和责任人，备份并验收后再升级。

## 0. 新增：离线完整快照与验证（不自动停服）

新增 `deploy/consistent_snapshot.py`，只使用 Python 标准库。它将主数据库、资金库、资金台账、`data/invoices/` 下的 PDF/隐藏 JSON/临时上传、`data/task_attachments/`、默认 `secret.key` 放在**同一个** ZIP 归档内，并为每个文件生成 SHA-256/长度清单。数据库通过 `sqlite3.Connection.backup()` 保存，清单验证同时检查两份 SQLite 的 `PRAGMA integrity_check`。归档输出权限为 `0600`（Linux），包含机密信息，严禁上传公开平台。

**只支持停写维护窗口**，不会误将在线 SQLite 热备份与不停变化的 PDF/JSON 声称为统一一致时点。需要先确认**所有服务进程和其他写入者**均已停止；脚本要求 `--offline-confirmed`，若检测到 `rm-progress` systemd 服务仍 active 则拒绝备份。

```bash
# 树莓派 / VPS 上，先按运维流程确认实际目录、版本及停机通知
sudo systemctl stop rm-progress
# 以实际运行用户执行；输出目录须存在且私有，不得使用公开 CI
python3 deploy/consistent_snapshot.py create \
  --app-dir /opt/rm-progress \
  --output /opt/rm-progress/backups/full-$(date +%Y%m%d-%H%M%S).zip \
  --offline-confirmed
python3 deploy/consistent_snapshot.py verify --archive /path/to/full-TIMESTAMP.zip
python3 deploy/consistent_snapshot.py restore \
  --archive /path/to/full-TIMESTAMP.zip --target /tmp/xtyf-recovery-new
# 注意 --target 必须完全不存在，切勿在生产运行目录恢复
# 隔离环境核对成员、金额、发票、截图和页面后，再考虑恢复生产服务
sudo systemctl start rm-progress
```

如密钥、DB、截图等通过环境变量重定向到安装目录之外，请先调整实际数据布局；本工具有意要求默认必要文件存在，不会在遗漏文件时宣称备份成功。它**不包含** systemd 配置、FRP/Nginx 配置及外部环境变量文件，这些需另外存放在受控运维备份中。恢复仅生成全新目录，不会覆盖线上目录或自动启动服务；从恢复目录迁回生产目录必须走人工停服切换和复核流程。

常规 `deploy/backup.sh` 继续执行历史每日数据库/每周发票**部分备份**，不会自动停止在线服务，也**不是**统一恢复点；上线前和重要变更前必须另外做本节的完整离线快照。

## 1. 为什么现有定时备份不够

`deploy/backup.sh`：
- 对 `data.db` 与 `data/funds/funds.db` 使用 SQLite `.backup`；默认为每日调用时留存相应日期快照。
- **仅在周日**打包 `data/invoices/`。
- **没有**把 `data/task_attachments/` 和 `secret.key` 纳入同一时点的统一恢复包。

因此不能用现有 cron 产物直接保证“任务 DB + 截图 + 资金 + 发票 + 密钥”的完整恢复。是否设置了每天 03:17 的 cron 也需要在服务器上实际检查，`deploy.sh` 不负责创建该 cron。

## 2. 升级前一致性快照

1. 在维护窗口确认当前部署版本、路径和管理员；告知用户暂停写入。最稳妥方式是先停止服务：`sudo systemctl stop rm-progress`。
2. 在同一个、权限受控的备份目录完整保存下列内容（路径相对于运行目录）：
   - `data.db` 及可能存在的 `data.db-wal` / `data.db-shm`；
   - `data/funds/`（包含资金库及相关文件）；
   - `data/invoices/`（包含隐藏 JSON、PDF 与临时上传）；
   - `data/task_attachments/`；
   - `secret.key`；
   - 部署配置、版本号和环境变量的**名称/备份位置**，不要把明文密钥写入公开记录。
3. 停止服务后可以同一时点完整复制文件；如用 `sqlite3.Connection.backup()` 或 `sqlite3 .backup`，也必须在停止写入的窗口完成全部数据库和关联文件的保存。
4. 恢复演练必须先在**隔离目录**进行，不能把生产数据直接交给自动化测试或公开 CI。

## 3. 隔离验证

对快照中所有 SQLite 库运行：

    sqlite3 /path/to/recovered/data.db "PRAGMA integrity_check;"
    sqlite3 /path/to/recovered/data/funds/funds.db "PRAGMA integrity_check;"

确认返回 `ok`；并核对成员、任务、日志、专业组、造车组、任务关系、修订、截图元数据和**实际文件数量/摘要**，以及发票 PDF/JSON 数量、资金记录与密钥的一致性。不能仅凭 HTTP 能登录判定恢复成功。

仓库提供**合成数据**演练（不读取生产密钥或票据）：

    python deploy/rehearse_collaboration_recovery.py

演练用于检查迁移和模拟恢复，不替代真实部署窗口的一致性快照与隔离核对。

## 4. 上线检查与回滚

- 在独立环境先升级并执行完整测试：
  
      python -m compileall -q app.py common.py modules tests
      python -m unittest discover -s tests -v

- 核对 `schema_migrations`、两套组别、成员软删除/恢复、任务关联、截图上传与权限。
- 人工验证资金审核授权与二次审核、发票上传/查重/确认、SSE 进度和 PDF 预览；部署模板仍保持 **1 worker / 8 threads**。服务需加载 `deploy/gunicorn.conf.py`，确认排队任务在重启后接续、整理/删除中断能显示待核对结果、撤销授权后排队任务不再执行。多进程运行须另行验收。
- 发票队列与审计在 `data.db`，须与 `data/invoices/` 一起恢复；停止全部 worker 后再恢复。不要在运行中删除 `.invoice.lock`，也不要混用本次实现与旧版本进程操作同一发票目录。
- 若部署失败，先**停止应用写入**；不能只把新代码回滚而无视自动数据库迁移。按恢复演练决定是保留兼容数据回滚代码，还是将 **同一个恢复点的 DB、附件、资金、发票、密钥一起恢复**。
- 确认恢复验证后再启动服务，复核日志、各角色入口、附件下载和财务统计。记录部署提交、备份路径和验收结论。

**禁止**将备份包、`secret.key`、真实成员资料或发票 PDF 放进公开 PR、工单或 GitHub Actions artifact。
