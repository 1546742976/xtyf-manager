## 迁移概览

`modules/task_migrations.py` 通过 `schema_migrations` 记录升级版本并用 SQLite 事务执行：

- v1：创建任务扩展关系（树、依赖、参与者、修订、截图等），从旧成员/任务字段迁移目录引用。
- v2：把历史中使用分号拼接的专业组拆分为多组关联，**仅一次**预置六个专业组。
- v3：新增 `member_projects`，**仅一次**根据历史任务的负责人/参与者与 `project_id` 推断成员参与的造车组别；默认预置步兵/哨兵/重装/飞镖，并保留旧细分项目。

`task_groups` 仍为历史数据/API 兼容存在，不再决定任务造车组别归属。`members.group_name` 与 `tasks.project` 等旧字段不是新关联的权威来源。

成员、专业组、造车组别的 `deleted_at` 表示软删除，管理员可恢复；**任务逻辑删除目前没有恢复入口**。

## 本轮安全与发票归属迁移

主应用初始化新增 `security_migrations`，与任务的 `schema_migrations` 分开计数：

- v1：添加 `members.must_change_password`、`member_permissions` 和 `security_audit`。现有账号默认不强制改密；新建、导入、重置与初始管理员必须改密。旧 `FUNDS_REVIEWERS` 仅在此时绑定已有成员 ID；当时有效的管理员/项管保留发票管理权限。
- v2：一次性处理发票元数据：姓名在所有成员（含停用/删除）中唯一时绑定 ID；同名、缺失、无效归属保留待确认。之后不再退回姓名授权，也不因新建同名成员重新认领。管理员先在“权限与审计”授权财务，财务在发票页筛选“归属待确认”，选择明确的成员 ID。

财务权限配置和请求审计入口为 `/admin/security`。审计不记录密码，不等于跨数据库事务。此前版本中断的历史任务审计仍可能保留“未完成”；旧进程内任务无法迁入新队列。

浏览器页面自动提交 CSRF；非浏览器客户端必须先取得 Cookie 和 `/api/csrf` 令牌，登录后更新响应头令牌。旧测试夹具也需接入首次改密和显式财务授权；本轮按要求未运行功能测试，迁移及浏览器验收仍待后续会话。

## 发票持久化队列与并发写入

`modules/invoice_jobs.py` 在主库中幂等创建 `invoice_jobs` 及索引，不改变任务/安全迁移版本。任务入队与开始审计、任务结束与结果审计分别在同一个 SQLite 事务内提交。队列本身不要求 PDF / JSON 格式迁移，后续金额缓存迁移见下文。

- `modules/invoice_storage.py` 使用线程可重入锁和操作系统文件锁，覆盖完整发票请求的读改写、后台任务、启动文件维护和命令行导出。锁文件为 `INVOICES_DIR/.invoice.lock`，运行中不得删除；队列列表/详情/SSE 不等待此锁。
- 每个进程最多一个调度线程；取得文件锁后才认领任务，并持续持锁直到结果落库。仅在取得此锁后处理遗留 `running` 状态，避免把正常但较慢的任务当成失联任务。
- `queued` 自动接续；中断的查重/金额刷新最多执行三次；整理/删除标为 `interrupted`，财务核对已发生的文件操作后再发起。PDF 和 JSON 之间仍无跨文件事务。
- 同类排队/执行中任务复用同一个 ID。执行前复核账号有效性、首次改密、会话版本和 `invoices.manage`；列表、详情与 SSE 只对财务开放。
- 前端展示最近 30 项任务；通过 `/invoices/api/jobs`、`/invoices/api/job/<id>` 和既有 SSE 查询持久状态与结果。记录不会因页面关闭或原半小时内存清理而丢失。
- `python app.py` 自动启动调度；Gunicorn 使用 `--config deploy/gunicorn.conf.py` 在 worker 启动后接续，包括 `--preload`。其他 WSGI 宿主可调用 `start_invoice_worker()`；未配置启动钩子时，首次登录后的发票请求触发调度。

部署模板仍为 1 worker / 8 threads；实现支持同机共享同一本地主库和发票目录的进程协作，不面向多主机/NFS。代码写入不表示多进程、权限变更和恢复流程已验收。备份必须同时包含主库中的队列/审计与发票文件；恢复前需停掉所有 worker。

## 金额迁移与统一规则

`modules/money.py` 是资金与发票共用的金额入口。每笔原始十进制金额按 `ROUND_HALF_UP` 四舍五入到分，再保存和计算；例如 `1.005` → `1.01`，两笔 `0.005` 各记 `0.01`，合计 `0.02`，不对未舍入的原值先求和。负数、布尔值、NaN/Infinity 和超界金额拒绝；资金舍入后必须大于零，发票允许零。单笔上限为 `92233720368547758.07` 元，汇总使用 Python 整数，不受 SQLite `SUM` 的 64 位累加溢出影响。

资金启动迁移由 `modules/funds_migrations.py` 在单个 SQLite 事务内完成，以 `funds_money_migrations` v1 标记：

- `records.amount_cents` 为权威整数分，`records.amount` 是由分值生成的两位金额文本，不接受直接写入。
- 原 ID、业务字段、审核状态和自增序列保留。历史 SQLite `amount` 原值及类型保存在 `funds_legacy_amounts`，用于核对；该表不参与运行时计算。
- 历史浮点先使用其十进制字符串表达，再按同一规则转分。某条历史金额无效时抛出包含记录 ID 的错误，整体回滚，不静默改零。已完成迁移再次启动不重算历史金额。
- 资金列表、统计、CSV、台账及图表金额标注都从整数分生成。统计和图表共用同一汇总逻辑；未指定来源、申请人、处理人的记录也分组计入，前端 Top 5/图表 Top 15 仍只是截取展示。

发票 `.invoice_cache.json` 在既有文件锁内原子升级为 `amount_cents` 整数，旧金额文本保留在对应条目的 `legacy_amount`；此字段随缓存条目生命周期保存，不替代备份。PDF/文件名提取同样使用十进制规则。新上传的人工确认金额保存为元数据 `confirmed_amount_cents`，优先于文件名、缓存和 PDF；历史记录没有该字段时保持原有取值顺序。资金库迁移与发票 JSON 迁移不是跨库事务。

**接口格式变化**：金额字段（`amount`、`total_in`、`balance`、分组 `total` 等）统一返回固定两位的字符串，同时提供 `*_cents` 整数字符串，防止浏览器大整数精度丢失。提交仍支持 JSON 数字或金额字符串；内置页面改为字符串，服务端从原始 JSON 按十进制解析。第三方客户端需同步适配，不能继续调用金额的 `.toFixed()` 或写入旧库 `amount` 列。前端金额格式化/比较用 `static/money.js`；浮点只用于图形坐标与百分比，不参与金额或金额标签计算。

本次包含生成列，需要 SQLite ≥ 3.31。升级应停止所有旧进程并保留统一恢复点，不能将旧代码直接连接已迁移的资金库。迁移及金额一致性功能测试按要求留给后续网页端会话。
