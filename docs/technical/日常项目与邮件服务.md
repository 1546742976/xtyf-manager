# 日常项目与邮件服务：配置、接口与验收

当前规则：北京时间每天 08:00 个人任务早报、22:00 团队项目晚报。下文标注“验收记录”的旧结果仅代表当时版本；本次早晚双邮件验证见文末。

## 数据与兼容

`modules/daily_schema.py` 在应用初始化中执行可重复的加法迁移：独立的 `daily_projects`、`daily_groups`、`daily_owners`、`daily_updates`、`daily_attachments`，以及 `member_email`、`mail_jobs`。旧 `tasks` / 造车 `projects` 结构与数据不转换。

日常项目图片位于 `TASK_ATTACHMENTS_DIR/daily`，沿用现有安全图片处理；默认目录已处于一致性快照的附件范围。主数据库包含邮箱、队列及项目数据；快照恢复必须同时保留数据库、附件和 `secret.key`。停服快照前也停止邮件 timer/service，避免发送进程继续写入。

成员邮箱仅在本人邮箱接口及管理员邮件接口返回，不加入 `/api/data`、成员通用资料或 CSV。六位验证码由服务端密钥与随机代号推导，数据库仅保存代号及经服务端密钥保护的校验摘要，不保存明文验证码；网站内填写完成验证，不通过邮件链接传递凭据。验证码和模拟 `.eml` 均为敏感内容，不写入日志、不上传 Git。旧链接验证凭据在升级迁移时失效，需重新申请验证码。

## 接口

日常项目现位于任务中心的“日常项目”页签：`/tasks?type=daily`；单个项目链接为 `/tasks?type=daily&project=<id>`。原 `/daily-projects` 与 `/daily-projects/<id>` 自动跳转，旧邮件和收藏仍可访问。未登录时，登录成功后返回相应项目；新邮件使用统一入口。此入口调整不把日常项目转换成造车任务，也不改变分组负责人、历史记录、附件和独立统计。邮件范围按下述早晚两类汇总规则执行。

造车页签位于 `/tasks?type=vehicle`，管理人员可用“新建任务”打开弹窗。桌面居中显示，窄于 768px 时占据可视区域；目标、人员、主前置任务与起止日期分组显示，底部保留提交与取消。关闭／重新打开保留当前草稿，保存失败保留输入；成功保存关闭弹窗并在页面反馈。工作台的 `#create` 链接直接打开该窗口。

| 接口 | 用途 |
|---|---|
| `GET/POST /api/daily-projects` | 20 项分页列表／管理角色创建；支持 `q,status,mine,page`，`dashboard=1` 返回独立工作台摘要 |
| `GET/POST /api/daily-projects/<id>` | 详情／管理角色修改，修改携带项目 `version` |
| `POST /api/daily-projects/<id>/delete` | 携带项目版本软删除 |
| `GET/POST /api/daily-projects/<id>/groups/<stage>/progress` | 20 项历史游标分页／提交进度，携带 `project_version,version,progress,note` 和可选 `files` |
| `GET /api/daily-projects/<id>/attachments/<id>` | 登录后读取仍可见项目的图片 |
| `GET /api/account/email` | 本人绑定和服务可用状态 |
| `POST /api/account/email/request` | `{email}`，受理验证请求；不等待 SMTP |
| `POST /api/account/email/verify` | `{code:"123456"}`，在账户页提交 6 位数字验证码完成邮箱绑定 |
| `GET /api/admin/mail?page=1` | 仅管理员查询成员状态和发送记录（30 条／页） |
| `POST /api/admin/mail/<id>/pause` | `{paused: true/false}`，仅管理员 |
| `POST /api/admin/mail/test` | 仅管理员向本人邮箱排队测试邮件 |

项目创建／修改的 `groups` 是启用组与负责人 ID 数组的映射，例如 `{"mechanical":[2,3],"vision":[3]}`。合法组固定为 `mechanical,electrical,vision`。提交的完整映射决定启用组，省略的已有组停用但保留历史。

进度为 0–100 整数；纯文字使用 JSON（普通请求 15 秒），含图片使用 multipart（180 秒）。每组维护进度版本，项目配置另有版本：跨组提交互不递增对方版本，配置变化或同组变化返回 409。所有权限在事务内重新校验，文件写入失败回滚。没有变更、备注或图片的空进度提交被拒绝。

## 个人任务早报与团队项目晚报

- 每天北京时间 **08:00** 发送个人任务早报，包括周末。只收录本人负责或参与的未完成造车任务、本人负责的未完成日常项目；项目仅展示本人负责的启用组，同一项目合并一项。完成、取消、软删除的事项不进入早报；没有个人未完成事项时跳过空邮件，不影响晚报。
- 早报主题为 `巡天御风｜个人任务早报｜YYYY-MM-DD`，提供 HTML 和纯文本，列出名称、角色或负责组、状态、进度、截止日期与剩余时间、最近进度更新时间及登录后的详情链接。无进度记录时明确标注并以创建／启用时间作为催更起点。

- 每天北京时间 **22:00**，包括周末，向每位有效、邮箱已验证且未被管理员暂停的成员分别发送一封晚报。没有个人分配也会收到团队简报；仅在全团队没有符合条件的事项时跳过空邮件。每封邮件只有一个收件人，不使用抄送或密送。
- 包含全团队造车任务和日常项目的未完成事项，以及北京时间当天完成的事项；已取消和软删除记录排除。日常项目展示所有启用组的进度。每项只列名称、状态、进度、截止提示和登录后可访问的详情链接，不附加完整日志、图片或其他成员邮箱。
- 主题为 `巡天御风｜团队项目晚报｜YYYY-MM-DD`，同时生成适配手机的 HTML 和纯文本。按**发送时快照**取数，22:00 发送后新完成的事项不会再追加邮件；这是一封晚报，不保证覆盖完整自然日内的所有完成事件。
- 最近一次进度记录距发送时**超过 48 小时**且进度不足 100% 时，只向当前收件人负责的造车任务或日常项目组显示“请更新进度”。造车参与者仅收到任务内容，不承担负责人催更；同组任一负责人更新后，该组其他负责人也重新计时。刚好 48 小时、已完成状态或进度 100% 不催更。
- 没有进度记录时，造车任务按创建时间、项目组按启用时间起算。修改标题、日期或负责人不重置进度计时；其他组更新不影响本组，重新启用组从重新启用时间计时。
- `tasks.completed_at` 和 `daily_projects.completed_at` 记录实际进入“已完成”的北京时间；普通编辑不刷新，重新打开后清除，任务撤销恢复对应历史值。迁移不会凭 `updated_at` 猜测旧记录的完成时间，缺少证据的历史已完成记录不作为“今日完成”发送。两个字段均通过可重复加法迁移添加，既有记录不搬迁。

## SMTP 与模拟模式

默认 `MAIL_MODE=off`，不发送、不受理新的验证请求。以下示例只说明配置项，不含实际凭据：

```ini
MAIL_MODE=preview
PUBLIC_BASE_URL=https://team.example.com
SMTP_HOST=smtp.example.com
SMTP_PORT=465
SMTP_TLS=ssl
SMTP_USERNAME=team@example.com
SMTP_PASSWORD=填写服务器上的邮箱授权凭据
SMTP_FROM=team@example.com
MAIL_PREVIEW_DIR=/opt/rm-progress/data/mail-preview
```

- `preview` 只生成私有 `.eml`；`smtp` 才实际投递；`off` 关闭处理。生产 SMTP 模式要求 HTTPS 正式站点地址。
- `SMTP_FROM` 填纯邮箱地址。`SMTP_TLS=ssl` 使用隐式 TLS（常见 465）；`starttls` 使用 STARTTLS（常见 587），端口以邮箱服务商实际配置为准，不支持明文降级。
- SMTP 连接超时 30 秒。授权码／密码只保存在服务器配置，不能提交仓库；真实地址、验证码和完整邮件正文不写入应用日志。SMTP 接受邮件不代表收件箱已送达。
- 验证码有效期 30 分钟；60 秒内不得重发，每小时最多 5 次；输错 5 次后当前验证码失效。再次申请会作废旧验证码，但保留管理员暂停状态。
- `.eml` 预览目录不暴露为静态文件；Linux 目录权限 0700、文件 0600，Windows 应置于当前用户的受限目录。预览文件可能含待办内容和有效验证码，不上传 Git。

命令：`venv/bin/python deploy/mail_worker.py`；`--preview` 强制模拟本次运行，仍需配置 `PUBLIC_BASE_URL`。此模式会领取队列并标记模拟完成，不能用在希望稍后真实发送的生产队列上。

### 163 邮箱接入

系统发件邮箱选用普通 `@163.com` 邮箱，接收成员仍可绑定自己的学校或其他邮箱。北京时间每天 **08:00** 发送个人未完成任务早报、**22:00** 发送全团队造车任务和日常项目简报；晚报包含未完成及当天完成事项，负责事项超过 **48 小时**未更新时提示催更。

配置模板为 [`deploy/mail-163.env.example`](../../deploy/mail-163.env.example)。复制到项目根目录已被 Git 忽略的 `mail.env`，填写完整发件邮箱、正式 HTTPS 站点地址，以及在网易邮箱客户端设置中生成的授权码。`SMTP_USERNAME` 与 `SMTP_FROM` 使用同一个完整邮箱地址；`SMTP_PASSWORD` 使用客户端授权码。连接使用 `smtp.163.com`、465 端口、`SMTP_TLS=ssl`（参见[163 邮箱 SMTP 配置说明](https://ioa.cloud.tencent.com/support/199262718652653568/#邮件通知源配置)）。

模板默认 `MAIL_MODE=off`，填写文件本身不会启动发送；Python 程序和 Windows 预览站也不会自动加载该文件。Linux 网站和发送进程须按下节加载同一 `EnvironmentFile`。真实地址和授权码只写本机或服务器配置，不写入示例、操作日志或聊天。正式站点及凭据齐备后，再单独执行真实邮件验收和发送服务启用；本机 `127.0.0.1` 不能作为团队邮件中的正式链接。

## Linux 定时服务（首次部署和升级自动处理）

首次运行 `bash deploy/deploy.sh` 时，`deploy/install_mail.py` 会自动建立或保留
`/etc/xtyf-manager/mail.env`（root 所有、0600），安装 `rm-mail.service`、
`rm-mail.timer`，以及网站服务 `rm-progress` 的共享环境配置。没有旧配置时，
按 163 模板创建 `MAIL_MODE=off`，**不启用 timer，也不发送邮件**。

如果旧运行目录已有 `mail.env`，且 `/etc/xtyf-manager/mail.env` 不存在，
安装器仅复制内容到受保护目录，不修改密码，也不删除旧文件（避免破坏手工
配置的 systemd drop-in）。`deploy.sh` 的 rsync 已排除旧 `mail.env`，
避免 `--delete` 误删；如旧文件仅存在于源码目录，请在首次部署前手动迁移到
`/etc/xtyf-manager/mail.env`，不要放进 Git。

升级时使用原来的打包 / `sudo python3 deploy/update_release.py` 流程：
先暂停邮件 timer 并等待正在运行的发送批次完成，再停止网站和创建一致性快照；
切换后自动更新邮件服务模板与网站环境 drop-in，保持独立配置文件不变。
如果原 timer 正在运行，升级成功或回滚后将其重新启动；原来未启用/未运行的
timer 仍保持未启用/未运行。不会因升级擅自启用发信。

管理员在服务器编辑配置（不要上传授权码到 Git 或聊天）：

```bash
sudoedit /etc/xtyf-manager/mail.env
# 为实际发信填写 SMTP_USERNAME/SMTP_FROM/SMTP_PASSWORD 和 HTTPS PUBLIC_BASE_URL，
# 然后将 MAIL_MODE=off 改为 MAIL_MODE=smtp
sudo systemctl restart rm-progress
# 先在网页绑定、验证管理员邮箱，再手动测试一次队列并核对收信
sudo systemctl start rm-mail.service
sudo journalctl -u rm-mail.service -n 50 --no-pager
# 确认真实送达后才明确启用每日定时处理
sudo systemctl enable --now rm-mail.timer
```

`/etc/xtyf-manager/mail.env` 不在发布包及应用运行目录内，升级无需重复填写。
单独运行 `python app.py` 不会自动加载 systemd 配置，开发环境仍需显式注入
环境变量。关闭自动处理可用 `sudo systemctl disable --now rm-mail.timer`；
只停 timer 不会清除已有邮件队列。

timer 从系统启动及前次处理结束后约 15 秒触发下一次队列检查（`AccuracySec=1s`）；验证／测试邮件优先于日报处理，空队列不连接 SMTP。业务使用固定 UTC+8 判断日期和时间，早报窗口为 **08:00（含）至 12:00（不含）**，晚报窗口为 **22:00（含）至当天午夜（不含）**；服务恢复后仅在对应窗口内补发，不补发往日邮件。领取时与实际处理前都会检查窗口，避免领取后超出窗口仍发送。验证和测试邮件不受早晚窗口约束，但验证有自己的过期时间。

队列按“成员 ID＋北京时间日期＋邮件类型”去重，SQLite `BEGIN IMMEDIATE` 原子领取。早报新增 `kind=morning`、`morning:日期:成员ID` 键；晚报保留 `kind=daily` 及既有键，升级不会把已发送晚报重新排队。早晚互不抵消，不需要迁移已有队列。管理员暂停同时作用于两类邮件。

发送前检查账号、邮箱版本、验证及暂停状态。明确临时错误最多 3 次；验证／测试邮件 60 秒后重试，早晚报至少间隔 15 分钟；重试仍须处于对应窗口，早报 11:45 及以后、晚报 23:45 及以后失败不再安排下一次重试。永久错误不重试。DATA 阶段断连保守标记未知；占用超过 30 分钟的中断任务也标记未知，不能自动重放。单次最多处理 200 条，下次 timer 继续处理。队列“SMTP 已接受”仅代表 SMTP 服务接受邮件，不保证进入收件箱。
